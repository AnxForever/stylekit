# StyleKit 混合语义检索（RAG）设计与实施

> 状态：设计已定稿，待实施
> 起点：`lib/knowledge/catalog.ts` 的 `searchKnowledgeCatalog`（纯词元重叠匹配）
> 目标：把关键词检索升级为「中文可用的混合检索（BM25 + 向量）」，并用评估集量化提升

## 1. 问题定义

### 1.1 已确认的缺陷（可复现）

`lib/knowledge/catalog.ts:45` 的分词函数：

```ts
function tokenize(value: string): string[] {
  return value
    .toLocaleLowerCase()
    .split(/[^\p{L}\p{N}]+/u)   // ← 缺陷根源
    .map((token) => token.trim())
    .filter(Boolean)
}
```

`\p{L}` 包含汉字，而中文书面语不使用空格分词，因此**整句中文会被切成一个 token**。实测：

| 查询 | token 数 | 结果 |
| --- | --- | --- |
| `我要一个适合金融后台的克制风格` | **1** | 整句作为单个 token |
| `深色夜景毛玻璃质感` | **1** | 整句作为单个 token |
| `dark mode dashboard` | 3 | 正常 |
| `glassmorphism frosted blur` | 3 | 正常 |

而匹配逻辑是整 token 相等：

```ts
const score = matchedFields.length / queryTokens.length
// matchedFields: queryTokens.some((token) => fieldTokens.has(token))
```

**结论：中文自然语言查询无法命中任何文档。** 但要注意——**这不是当前唯一的原因，也不是当前影响最大的原因。**

### 1.1.1 两层问题必须分开（重要）

实测 `loadKnowledgeCatalog()` 在当前仓库状态下**返回空数组**：`knowledge/manifests/` 下 10 个文件全部是 `reviewStatus: pending` + `publicationStatus: unpublished`，而 `isRetrievable` 要求两者分别是 `approved` 和 `published`。

也就是说，**当下英文查询和中文查询都是 0 命中**——文档根本没进索引。这是**发布状态层**的问题，与分词无关。

把这一层剥掉之后，分词缺陷才独立显现。`tools/scripts/measure-retrieval-baseline.ts` 实测（每组 10 / 10 / 8 条查询）：

```
method                                            zh-intent(10)   zh-term(10)        en(8)
A. 生产实现 searchKnowledgeCatalog（知识库语料）        0/10 0.0%     0/10 0.0%    3/8 37.5%
B. 复刻匹配器 + 旧分词（风格语料 148 条）               0/10 0.0%    5/10 50.0%   8/8 100.0%
C. 复刻匹配器 + 新分词（风格语料 148 条）             10/10 100.0%  10/10 100.0%  8/8 100.0%
```

**B 与 C 只差分词器，这是唯一的自变量。**

### 三条必须同时成立、否则数字会被误读

1. **准确说法是「中文自然语言查询 0%」，不是「中文 0%」。** zh-intent（「我要一个适合金融后台的克制风格」这类）在 A、B 两组都是 0/10；但 zh-term（「毛玻璃」「玻璃拟态」这类短术语）在 B 组是 **5/10**——因为风格的 `keywords` 字段是用空格拼接的，短术语本身就是独立的空格分隔 token，整 token 相等的匹配会歪打正着。查询集拆成 intent / term 两组就是为了不把真实的 0 平均成一个好看的数字。
2. **C 组的 100% 是「返回了东西」，不是「返回对了」。** 它证明的是旧分词**完全无法召回**，不证明新分词召回得**准确**。相关性质量（Recall@K / MRR / NDCG）是 P3 评估集的事，baseline 脚本不做。
3. **A 组必须用 `includeUnpublished: true` 才能拿到 10 条知识库资源**，否则英文那列也会是 0，失去对照意义（见 1.1.1）。

注意 A 与 B/C 跑在**不同语料**上（知识库 vs 风格库），横向不可直接比较；B 与 C 才是受控对照。

> 方法论提醒：不能把「中文 0 命中」直接当成缺陷证据。**混了两层原因的观察不是证据。** 必须先控制变量，剥掉发布状态这一层，剩下的一致性差异才能归因。

### 1.1.2 缺陷的作用范围

这个缺陷只在**知识库检索**（`lib/knowledge/catalog.ts`），影响的是 advisor 的知识召回。

**风格搜索走的是另一条路**：`lib/discovery.ts` 的 `searchStyles`，用子串 `includes` 加双语同义词扩展，**没有这个缺陷**。

换句话说：项目里唯一用「切词 + 全等匹配」的地方，正好是唯一在中文上归零的地方。

本项目要修的也是这条路径（知识库召回），不是风格搜索。

### 1.2 为什么不能只修分词（本节结论已被评估推翻，见下）

补上中文分词（jieba / Intl.Segmenter）能修复字面命中，但仍然无法解决：

- **同义表达**：毛玻璃、玻璃拟态、frosted glass、backdrop-blur 互为同义
- **意图描述**：「适合金融后台的克制风格」——当时认为没有任何一个词出现在任何风格文档里
- **跨语言**：中文提问检索英文文档（本站文档中英双份，但用户查询只匹配一侧）

原结论是「这些只有语义检索能解决，分词修复是可选的加速项，不是方案」。

> **实施后修正（2026-09-17）：这条结论是错的。**
>
> §5.4 的评估显示：**修好分词 + BM25 之后，中文口语化意图那一组的 Recall@1 是 80.0%，修之前是 0%。**
>
> 也就是说，「金融后台」「克制」这些词**本来就在风格文档里**。不是「词没出现过」，是「出现过，但分词器切不开，所以字面命中失效」。**上面第二条论据不成立。**
>
> 这一组同时换掉了匹配算法（旧的词元重叠 → BM25），不能把 80% 全算在分词头上；但主因是分词——同一份 BM25，只把分词器换回有缺陷的那个，这一组立刻掉回 0%。
>
> 同义表达与跨语言两类问题仍在，只是它们在标注集里的占比比这里原先估计的低。
>
> **语义检索在这个基础上还有多少增益**，已在配好 API key 后测出：整体 Recall@1 从 80.0% 升至 96.7%（§5.4）。原先「只修分词不够」的判断在方向上说对了（向量层确实还有增益），但把增益的量级估计错了——分词修复承担的是主要部分（35.0% → 81.7%），向量层补上的是剩余部分。

### 1.3 成功判据

- 中文自然语言查询的 Top-3 命中率从 **0%（现状）** 提升到 **≥ 80%**
  - **已达成，且未依赖向量层**：修好分词 + BM25 后该组 Recall@1 已达 80.0%（§5.4）
- 英文查询不退化（NDCG 不低于现状）—— 待真实向量下复测
- 检索延迟 P95 < 150ms（含向量查询）—— 索引侧实测 p95 为 340ms，**不满足**；但该数字不含真实 embedding 往返，两端都还需生产环境验证（见 §5.4）
- 向量服务不可用时自动降级到关键词检索，**不报错、不空转** —— 已实现并有测试

## 2. 数据源与切片策略

### 2.1 语料

| 来源 | 规模 | 字段 | 位置 |
| --- | --- | --- | --- |
| 设计风格 | 148 条 | `description` / `philosophy` / `doList` / `keywords` | `lib/styles/registry.ts` |
| 风格包 | 同上 | `components` / `recipes`（组件配方） | `getStylePack(slug)` |
| 知识库文档 | `knowledge/manifests/*.json` | `summary` / `tags` / `useCases` / `topics` | `lib/knowledge/catalog.ts` |

> 风格数 148、动画数 60 以运行时注册表为准。**不要用 `ls lib/styles/*.ts | wc -l` 计数**（那是文件数 181，含 tokens/helpers，会虚高）。

### 2.2 切片（chunking）

**策略：按语义字段切，不按字数切。**

每种风格产出多个 chunk，每个 chunk 带类型标签，检索时按类型加权：

| chunk 类型 | 内容 | 用途 | 权重 |
| --- | --- | --- | --- |
| `identity` | `name` + `description` + `keywords` | 精确风格名匹配 | 1.0 |
| `philosophy` | `philosophy` 正文 | 语义/意图匹配（**主力**） | 1.2 |
| `rules` | `doList` 条目 | 约束类查询 | 1.0 |
| `recipes` | 组件配方摘要 | 实现类查询 | 0.8 |

`philosophy` 权重最高的理由：它是长文本、语义密度大，正是 embedding 的主场；而 `identity` 短文本用关键词就能命中，向量收益低。

> **实施后修正（2026-09-17）：这套权重已从实现中移除。**
>
> 上面把它描述成「nudge（轻推）」，实测不是。RRF 在 k=60 时分数区间很窄：
>
> ```
> rank  1  →  1/61 = 0.016393
> rank 13  →  1/73 = 0.013699      相差 16%
> ```
>
> `1.2/(60+r) ≥ 1/61 ⟺ r ≤ 13.2`：一条排进前 13 名的 `philosophy` chunk，得分高过全语料排第 1 的 `identity` chunk。locale boost 1.1 单独对应 r ≤ 7.1，两者叠加 1.32 对应 r ≤ 20.5。
>
> 60 条 query 中，28 条的 rank-1 因加权改变，54 条的 top-5 改变。
>
> 同一份 BM25 排序，只差事后加权，整体 Recall@1 从 81.7% 降到 63.3%。
>
> 在 RRF 之后乘权重，把 §3.3 选择 RRF 时要规避的分数尺度敏感性又引了回来。§2.2 与 §3.3 在原稿里是矛盾的。
>
> 加权已移除。数据见 §5.4。

**下限**：单 chunk < 32 字符不单独建索引（信息量不足，会引入噪声近邻）。

### 2.3 跨语言

`philosophy` 与 `philosophyEn` 分别 embedding，**共用同一个向量空间**（DashScope 多语言模型天然对齐中英）。这样中文查询可以直接召回英文 chunk，反之亦然。

保留 `locale` 元数据用于「同语言优先」的加权，但不做硬过滤——否则会丢掉跨语言召回。

## 3. 技术选型

### 3.1 Embedding

- **模型**：DashScope `text-embedding-v4`（阿里百炼，已有 `DASHSCOPE_API_KEY`）
- **维度**：1024（v4 支持 512/768/1024/1536，1024 是质量/成本折中点）
- **批处理**：DashScope 单次上限 25 条 → 分批 + 并发 3，全量 148 风格约 600 chunk，**首次全量约 30 秒**
- **缓存**：以 `content_hash` 为键缓存向量，内容不变不重算 —— 风格文档改动频繁（仓库 7 个月 1223 次提交），这是必须的

> 备选：本地 `bge-m3`（无 API 成本、无网络依赖），但引入模型体积与冷启动开销。**先用 DashScope，把 provider 抽象成接口**，后续可切换。

### 3.2 向量存储

**选 `sqlite-vec`。**

理由（对比 pgvector / LanceDB / 纯内存）：

- 贴合现有技术栈（项目已在 `resume-agent` 用 SQLite 做 durable run store）
- **零新增运维**——不需要起 Postgres 服务，自有服务器是内存受限的（CLAUDE.md 明确写了部署规则）
- 与 FTS5 同库，**混合检索可以在一条 SQL 里做**，不用跨系统对账
- 148 风格 × 4 chunk ≈ 600 向量，**暴力检索就够快**，HNSW 索引都用不上

> 放弃 pgvector：为 600 个向量起一个 Postgres 不值得。
> 放弃纯内存：进程重启要重新加载，且无法与 FTS5 联表。

> **实施后修正（P1/P2 已落地）**：项目当前**没有 `sqlite-vec`，也没有 `better-sqlite3`**（已验证，且未安装）。因此 P1/P2 的实际实现是：
>
> - **向量路**：`lib/retrieval/vector-store.ts` 用纯 TypeScript 暴力余弦检索，向量落盘为 JSON。
> - **关键词路**：`lib/retrieval/hybrid-search.ts` 用纯 TypeScript 实现的 BM25（`k1=1.2`、`b=0.75`），**没有用 FTS5**。
>
> 评分逻辑与本节设计等价，但「与 FTS5 同库、一条 SQL 搞定」这一条**尚未兑现**——它需要先装 SQLite binding。这不是取舍失误，是环境约束下先跑通闭环；等 binding 到位再迁移，接口已经留好（`VectorStore`）。
>
> 实测性能（1030 chunk）：建索引 189ms、重开索引 19ms、纯暴力检索查询 3–6ms。完整混合检索（BM25 + 向量 + RRF）的索引侧延迟为 p50 139ms / p95 340ms，**不含真实 embedding 往返**；该数字高于 §1.3 设定的 150ms 目标，需在生产环境复核。

### 3.3 检索融合

**RRF（Reciprocal Rank Fusion）**，不做加权求和：

```
score(d) = Σ_over_retrievers  1 / (k + rank_r(d))      // k = 60
```

选 RRF 而非加权求和的理由：**两路检索的分数不可比**——BM25 是无界实数，余弦相似度是 [-1,1]。归一化会让结果对分数分布敏感，而 RRF 只用**排名**，免调参、鲁棒。这是工业界混合检索的默认选择。

### 3.4 Rerank

首期**不引入独立 rerank 模型**。理由：候选集只有 ~20 条，直接让现有的 LLM 在生成推荐时看完整候选即可，收益不足以抵消一次额外调用。

留接口：`rerank?(query, candidates) => candidates`，后续接 cross-encoder 或 LLM rerank。

## 4. 架构

```
用户查询
   │
   ├─→ [查询改写] LLM 抽取风格意图关键词（口语 → 检索友好）  ← 可选，失败则用原句
   │
   ├─→ [关键词检索] SQLite FTS5 (BM25)          ─┐
   │                                              ├─→ RRF 融合 → Top-K
   └─→ [向量检索] sqlite-vec (余弦, 1024维)     ─┘
                                                  │
                                                  ├─→ locale 加权（同语言 1.1；chunk 类型加权已移除）
                                                  │
                                                  └─→ [生成] 现有 requestStyleIntent
```

**降级链**（必须实现，这是「生产化」与「demo」的分水岭）：

1. 向量服务超时/报错 → 只用 FTS5，标记 `degraded: true`
2. FTS5 也无结果 → 返回空候选，让 LLM 自由发挥（**与现状行为一致，不引入回归**）
3. 查询改写失败 → 用原句直接检索

## 5. 评估

### 5.1 评估集

构造 **query → 期望风格 slug** 的标注集，≥ 60 条，覆盖：

| 类型 | 条数 | 示例 |
| --- | --- | --- |
| 中文口语化意图 | 20 | 「我要做金融后台，想要克制冷静一点」→ `swiss-style` |
| 中文风格术语 | 15 | 「毛玻璃」→ `glassmorphism` |
| 英文自然语言 | 15 | "clean apple-like landing page" → `apple-style` |
| 跨语言 | 10 | 中文提问 → 英文文档命中 |

标注要求：每条给出 **1 个主答案 + 2 个可接受备选**，评分时备选算部分正确。

### 5.2 指标

- **Recall@K**（K = 1, 3, 5）——主要指标
- **MRR**（Mean Reciprocal Rank）——衡量主答案的排名
- **NDCG@5**——考虑多级相关性

### 5.3 对照实验

原稿写「A vs B 隔离出只修分词」——**这是错的**。实际跑下来必须拆成三段读，每段隔离的变量不同：

| 对照 | 隔离出的变量 | 是否单变量 |
| --- | --- | --- |
| A vs B | 分词器 **和** 匹配算法同时换了 | 不是 |
| **B vs B'** | 只隔离「融合后加权」 | 是 |
| **B' vs C** | 只隔离「向量路」 | 是 |

B' 是实跑时补的一行（混合检索把向量路关掉、走降级链），**它反而是这张表可归因的关键**——没有它，B vs C 会同时混进「向量路」和「加权」两个变量。

> **唯一真正只差分词器的受控实验是 §1.1 用的 `tools/scripts/measure-retrieval-baseline.ts`**（同语料、同匹配器、只换分词器）。**两张表的数字不能跨表比较**——口径不同：那边是 hit rate@5，这边是带分级标签的 Recall@1/MRR/NDCG。

### 5.4 实测结果（2026-09-17，60 条标注集，真实 embedding）

`tools/scripts/evaluate-retrieval.ts --top-k 5`。C 组使用 DashScope `text-embedding-v4` 构建的真实索引（1030 chunk / 1014 条唯一文本，构建耗时 19.1s）。

各组整体指标：

| 组 | 说明 | Recall@1 | Recall@3 | MRR | NDCG@5 |
| --- | --- | --- | --- | --- | --- |
| A | 基线：分词缺陷 + 旧匹配器 | 35.0% | 40.0% | 0.378 | 0.269 |
| B | 修好分词 + 纯 BM25 | 81.7% | 93.3% | 0.876 | 0.710 |
| B' | 同 B，加 locale boost，关闭向量路 | 80.0% | 91.7% | 0.860 | 0.699 |
| C | 混合检索（BM25 + 向量 + RRF） | 96.7% | 98.3% | 0.978 | 0.811 |

分类 Recall@1：

| 组 | 中文口语化意图(20) | 中文术语(15) | 英文(15) | 跨语言(10) | 整体(60) |
| --- | --- | --- | --- | --- | --- |
| A | 0.0% | 73.3% | 40.0% | 40.0% | 35.0% |
| B | 80.0% | 86.7% | 80.0% | 80.0% | 81.7% |
| B' | 80.0% | 86.7% | 80.0% | 70.0% | 80.0% |
| C | 90.0% | 100.0% | 100.0% | 100.0% | 96.7% |

索引侧延迟（不含真实 embedding 往返）：A 组 p50 15ms / p95 18ms；B、B' 组 p50 0ms / p95 1ms；C 组 p50 139ms / p95 340ms。

#### 各对照隔离出的变量

§5.3 已说明 A 与 B 之间同时换掉了分词器和匹配算法。四组两两比较的读法如下：

- **A → B**：分词器与匹配算法同时改变，不是单变量。整体 Recall@1 从 35.0% 升至 81.7%，中文口语化意图从 0.0% 升至 80.0%。这一级台阶最大，但归因需要谨慎。
- **B → B'**：仅增加 locale boost。整体 Recall@1 从 81.7% 降到 80.0%，差距来自 1 条 query（`cross-lingual-08`）。该加成在 60 条上的战绩为 0 胜 1 负。样本量不足以支持删除，保留待复测。
- **B' → C**：仅增加向量路。整体 Recall@1 从 80.0% 升至 96.7%，净增 16.7 个百分点。跨语言组从 90.0% 升至 100.0%，与 §2.3 的预期一致——该组中「某中文词只出现在英文副本」的条目是唯一必须依赖共享向量空间才能召回的部分。

加权曾经在此表中单独占一行（B''），移除前后见 §2.2 的说明。

#### 关于早期那次假向量结果

本机此前没有 `DASHSCOPE_API_KEY`，C 组一度使用确定性假向量运行，得到的数字（整体 Recall@1 60.0%）低于 B 组。该结果不反映向量检索的真实效果，记录在此仅作为评估框架有效性的旁证：该框架能区分真实 embedding 与噪声向量，说明它对语义层的变化是敏感的。

#### 本次实跑发现的实现缺陷

首次调用真实 embedding 接口时返回 HTTP 400：

```
batch size is invalid, it should not be larger than 10
```

`MAX_BATCH_SIZE` 原为 25，取自本文档 §3.1 的估算。该错误未被任何单元测试捕获，原因是测试全部注入假 provider，从未触达真实限制；设计文档、实现与测试使用同一个错误数值，因此三者相互印证而非相互校验。已改为 10，并在 `lib/retrieval/embedding.ts` 中注明该值来自实跑而非文档。

#### 标注质量

评估集由人工标注，以下条目相关性偏弱，引用数字时需知悉：

- `zh-intent-01`（「金融后台，克制冷静」）原标注为 `swiss-style`，但 `stripe-style` 同样成立且未列入备选，导致旧匹配器的一个合理 top-1 被计为未命中。已将其换入备选（同时移出相关性较弱的 `data-dense`）。修正后 B 组整体 Recall@1 由 80.0% 升至 81.7%。
- `zh-intent-06`、`cross-lingual-05`、`cross-lingual-09`、`cross-lingual-10`、`zh-term-02`、`en-12` 的标注可辩护但不唯一，未作修改。

**要写的是「量化了检索改进」，不是「做了个 RAG」。** 前者已被数据支持（A→B），后者尚未被证明（B'→C 无结论）。真实数字见 §8。

### 简历条目

> 发现站内中文检索存在分词缺陷（`\p{L}` 将整句中文识别为单个 token）；先排除了一个更容易被误认的原因（知识库文档全部处于未发布状态），再定位到分词层；构建 60 条中英双语分级标注评估集（Recall@K / MRR / NDCG）量化改进，整体 Recall@1 从 35.0% 提升至 96.7%，中文自然语言查询从 0.0% 提升至 90.0%。

可拆成两条写，也可以合成一条。如果只保留一句，保留前一句（发现缺陷并量化），因为它的因果链更完整。

### 面试展开

第一层，缺陷定位：

> 站内中文检索完全不工作。我先查到一个更容易被误认的原因——知识库的 10 个文档全部处于未发布状态，所以中英文都是 0 命中。把这一层剥掉之后，才看到真正的缺陷在分词：`\p{L}` 包含汉字，而中文不用空格分词，整句会被切成一个 token，字面匹配永远命中不了。

第二层，量化与结论：

> 我建了一套 60 条标注评估集来量化。修好分词后整体 Recall@1 从 35% 到 81.7%，中文自然语言从 0% 到 80%。再加上向量层后到 96.7%——跨语言那一组从 90% 到 100%，因为有几条查询的关键证据只存在于英文副本里，只有共享向量空间能连起来。

第三层，如果被问到「有没有走过弯路」：

> 有。我按设计实现了 chunk 类型加权，评估显示它让 Recall@1 掉了 18 个百分点。原因是 k=60 时 RRF 的分数区间很窄，1.2 的权重实际相当于十几名的差距，不是我在设计文档里写的「轻推」。更根本的问题是，在 RRF 之后乘权重，等于把 RRF 当初要规避的分数尺度敏感性又引了回来。我把权重删掉了。

第三层不是必答题。但它是这几段里唯一能体现「会检验自己的设计」的部分，问到就该讲。
